# 인터페이스 컨벤션
## 0) 목표

- 구현을 안 보여줘도(블랙박스) 테스트를 정확히 설계하려면, 인터페이스에 **기능 계약(성공/실패/권한/검증/부수효과)**가 명시돼야 한다.
    
- MVC에서 테스트 “설계의 기준점”은 보통 **Service 인터페이스**다.
    
    - Controller는 HTTP/바인딩 책임이므로(별도 테스트)
        
    - “업무 규칙”은 Service 계약에서 정의해야 한다.
        

---

## 1) 인터페이스 계층 규칙 (MVC 기준)

### 1.1 Service 인터페이스를 기준으로 작성

- 예: `AuthService`, `RoomService`, `InviteService`, `UserService`
    
- 인터페이스에는 **업무 기능 단위 메서드**만 존재
    
- 트랜잭션/저장/검증 같은 정책은 **주석 계약으로 고정**
    

### 1.2 Controller는 계약의 “복사본”을 만들지 않기

- Controller는 경로/HTTP 메서드/DTO 변환만 담당
    
- “실패 시 어떤 에러인지” 같은 핵심 계약은 **Service 인터페이스에만** 둔다  
    (그래야 블랙박스 테스트가 Service 기준으로 뽑힘)
    

---

## 2) 메서드 시그니처 규칙 (MVC 최적화)

### 2.1 반환형은 무조건 `Result<T>`

- 예외/nullable로 신호를 섞지 않는다.
    
- 값이 없으면 `Result<Void>`로 통일.
    

### 2.2 입력은 DTO로 묶는다

- 파라미터 2개 이상이면 무조건 요청 DTO(=Command/Request)로 묶는다.
    
    - ✅ `Result<Long> createRoom(CreateRoomRequest req, Long requesterUserId)`
        
    - ✅ `Result<Long> createRoom(CreateRoomRequest req, AuthUser auth)` (인증 정보를 묶는 경우)
        
    - ❌ `Result<Long> createRoom(Long userId, String name, String repo, ...)`
        

### 2.3 인증 정보 전달 방식은 1개로 통일

블랙박스 테스트 설계를 위해 “누가 호출하는지”가 항상 동일 방식으로 들어와야 함.

- 방식 A: `requesterUserId`를 파라미터로 받는다
    
- 방식 B: `AuthUser` 같은 객체를 받는다
    
- 방식 C: Service는 userId를 안 받고 Controller에서 이미 식별된 userId만 넘긴다(권장)
    

> 어떤 방식을 택하든 **프로젝트 전체에서 하나로 통일**.

## 3) Service 메서드 Javadoc “계약 블록” 강제 (필수)

MVC에서 블랙박스 테스트를 잘 뽑으려면, Service 메서드 위에 아래 블록을 **반드시** 적는다.

### ✅ Contract Block 템플릿 (복붙용)

```java
/**
 * Action: (무엇을 개발/제공하는 기능인지 1줄)
 * Input:
 *  - (필수값/제약/null 가능 여부/형식/경계값)
 * Success:
 *  - ok(...) : (반환값 의미 / 값이 없으면 ok())
 * Auth/Permission:
 *  - (로그인 필요? / 본인만? / owner만? / 참여자만?)
 * Persistence:
 *  - (읽기/저장 여부, 성공 시 save 호출 여부)
 * Idempotency:
 *  - (멱등/비멱등/중복 요청 처리)
 * Failures:  // ★ 블랙박스 테스트의 핵심
 *  - <HTTP_CODE>: <조건> (metadata: {key1, key2...})
 *  - <HTTP_CODE>: <조건> (metadata: {...})
 */
```

---

## 4) Failures(에러 계약) 컨벤션 (ResultError 기반)

`ResultError.getCode()`가 사실상 HTTP Status이므로, 실패 계약은 **HTTP 코드 중심**으로 작성한다.

### 4.1 실패 케이스는 “분기별로” 나열

- 400 Validation
    
- 401 Unauthorized(로그인 필요)
    
- 403 Forbidden(권한 없음)
    
- 404 Not Found
    
- 409 Conflict(중복/상태 충돌)
    

### 4.2 metadata 키를 표준화(테스트 가능한 계약)

에러마다 metadata에 **반드시 넣는 키**를 고정하면 블랙박스 테스트가 강해진다.

권장 표준:

- 404: `{resource, id}`
    
- 403: `{resource, id, userId}`
    
- 409: `{resource, key}` 또는 `{resource, id, userId}`
    
- 400: `{field, reason}` 또는 `{fields:[...]}`
    

> message는 고정하지 말고(code + metadata)만 고정하는 게 유지보수에 유리.

---

## 5) Validation(입력 제약) 주석 규칙

Request DTO(예: `CreateRoomRequest`) 또는 Service 계약에 아래를 명시한다.

- not null / not blank
    
- 길이 제한
    
- 형식(정규식 등)
    
- 허용값(enum 범위)
    
- 경계값(최소/최대)
    

---

## 6) Persistence(저장/부수효과) 주석 규칙

Service는 보통 저장을 수행하므로, 블랙박스 테스트가 `save` 호출 여부까지 설계 가능하게:

- 성공 시 저장 1회/다회 여부
    
- 실패 시 저장 없음(가능하면 명시)
    
- 이벤트 발행/캐시 갱신 등 부수효과도 있으면 명시
    

---

## 7) 멱등성/중복 정책 주석 규칙

- “같은 요청을 다시 보내면?”을 반드시 적는다.
    
    - 새로 생성(비멱등)
        
    - 기존 반환(멱등)
        
    - 409 반환(충돌)
        
- 특히 join/초대/생성 같은 기능은 테스트 분기가 여기서 갈린다.

## 8) MVC에 맞춘 인터페이스 예시 

```java
public interface RoomService {

    /**
     * Action: 방을 생성한다.
     * Input:
     *  - requesterUserId: not null
     *  - req.name: 1~50자, not blank
     * Success:
     *  - ok(roomId): 생성된 방 ID 반환
     * Auth/Permission:
     *  - 로그인 필요, requesterUserId는 로그인 사용자
     * Persistence:
     *  - 성공 시 room 저장 1회, 실패 시 저장 없음
     * Idempotency:
     *  - non-idempotent (호출마다 새 방 생성)
     * Failures:
     *  - 400: name invalid (metadata: {field:"name", reason})
     *  - 401: not logged in (metadata: {reason})
     */
    Result<Long> createRoom(Long requesterUserId, CreateRoomRequest req);

    /**
     * Action: 내 방 목록을 조회한다.
     * Input:
     *  - requesterUserId: not null
     * Success:
     *  - ok(list): 방 리스트 반환
     * Auth/Permission:
     *  - 로그인 필요
     * Persistence:
     *  - read-only
     * Idempotency:
     *  - idempotent
     * Failures:
     *  - 401: not logged in (metadata: {reason})
     */
    Result<List<RoomSummary>> getMyRooms(Long requesterUserId);

    /**
     * Action: 방 참여자 목록을 조회한다.
     * Input:
     *  - requesterUserId: not null
     *  - roomId: not null
     * Success:
     *  - ok(list): 참여자 리스트 반환(최소 필드: id, name, avatarUrl)
     * Auth/Permission:
     *  - 로그인 필요, 방 참여자만 가능
     * Persistence:
     *  - read-only
     * Failures:
     *  - 401: not logged in (metadata: {reason})
     *  - 403: not participant (metadata: {resource:"room", id:roomId, userId:requesterUserId})
     *  - 404: room not found (metadata: {resource:"room", id:roomId})
     */
    Result<List<UserSummary>> getParticipants(Long requesterUserId, Long roomId);
}
```
