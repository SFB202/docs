    패키지 구조 컨벤션¶

    0) 목적¶

    • 전통적인 MVC 구조에서 책임을 분리해 코드 위치를 예측 가능하게 만든다.

    • api는 HTTP/Web 책임, service는 비즈니스 로직, data는 저장소/외부 연동을 담당한다.

    • “어디에 뭘 넣어야 하는지”를 문서로 고정해 폴더 난립을 막는다.

    1) 레이어 개요¶

    api     : 웹(HTTP) 계층 — Controller, Request/Response DTO, Security, Web Config
service : 비즈니스 계층 — 서비스 인터페이스/구현, command/query
data    : 데이터/연동 계층 — DB Entity, Repository, External Client, data 전용 util

    요청 처리 흐름(원칙)¶

    api.controller → service.service → data.repository/external → 결과 반환

    • 요청/응답 DTO는 api.request / api.response

    • 서비스 입력 모델은 service.command / service.query

    2) 패키지별 책임과 규칙¶

    2.1 api/¶

    HTTP 요청을 받는 웹 계층.

    api.controller¶

    • @RestController만 위치

    • 책임

      • URL 라우팅, 파라미터 바인딩

      • @Valid 기반 입력 검증(Bean Validation)

      • service 호출 및 응답 변환

    • 금지

      • DB 직접 접근(data.* 직접 호출은 가능하나 Repository 직접 호출은 금지 권장)

      • 비즈니스 규칙 판단(중복/권한/상태 등)

    api.request¶

    • Controller 입력 DTO (record 권장)

    • 규칙

      • jakarta.validation 애너테이션은 여기에서만 사용

      • 가능하면 toCommand() / toQuery() 변환 메서드를 제공해 변환 책임을 DTO에 둔다(선택)

    • 금지

      • data.entity 같은 내부 모델 참조

    api.response¶

    • Controller 출력 DTO

    • 규칙

      • 엔티티/내부 모델을 그대로 노출 금지

      • 민감정보(비밀번호/토큰 등) 포함 금지

    api.security¶

    • Spring Security 관련(필터, 인증 객체, SecurityConfig 등)

    • 규칙

      • 인증/인가 처리는 여기에서 담당

      • Controller/Service에는 “로그인 사용자 id” 정도만 전달되도록 설계 권장

    api.config¶

    • 웹 관련 설정(CORS, Jackson, ArgumentResolver, Interceptor 등)

    • 규칙

      • DB 설정/Repository 설정은 여기 두지 않는다(그건 data/config 성격)

    2.2 service/¶

    비즈니스 로직 계층.

    service.service¶

    • 서비스 인터페이스(또는 클래스)를 위치시킨다.

    • 규칙

      • 반환 타입은 팀 표준대로 Result<T> 사용 권장

      • 메서드 입력은 가능하면 service.command/query를 사용한다.

    service.service.impl¶

    • service.service의 구현체만 위치

    • 규칙

      • 트랜잭션(@Transactional)은 보통 여기서 선언

      • 데이터 접근은 data.repository, 외부 연동은 data.external을 통해 수행

    • 금지

      • Controller DTO(api.request/response)를 파라미터/리턴으로 직접 사용(원칙적으로 금지)

    service.command¶

    • “상태 변경” 입력 모델 (Create/Update/Delete)

    • 예: CreateUserCommand, UpdateRoomCommand

    • 규칙

      • 웹 validation 애너테이션 최소화(가능하면 service 로직에서 Result로 처리)

      • 불변 객체 권장(record 가능)

    service.query¶

    • “조회” 입력 모델(검색/필터/페이징)

    • 예: GetRoomListQuery, SearchBarQuery

    2.3 data/¶

    데이터/연동 계층.

    data.entity¶

    • DB 테이블 매핑 엔티티(JPA Entity 등)

    • 규칙

      • 외부 API DTO/응답 모델을 여기 넣지 않는다.

    • 금지

      • api.response로 직접 반환(노출 금지)

    data.repository¶

    • DB 접근 구현체

      • Spring Data JPA Repository / MyBatis Mapper / QueryDSL repository 등

    • 규칙

      • service가 직접 주입받아 사용해도 됨(이번 프로젝트는 클린아키텍처 강제 X)

      • 단, Controller가 repository를 직접 호출하는 것은 금지(service 경유)

    data.external¶

    • 외부 API 연동(HTTP Client, OAuth, 공공데이터 등)

    • 규칙

      • 외부 요청/응답 DTO는 data.external 하위로 함께 둔다(예: data.external.dto)

      • 외부 연동 실패는 service에서 Result.fail(new ServerError(...)) 또는 적절한 error로 변환

    data.util¶

    • data 계층 한정 유틸

    • 규칙

      • 전역 유틸처럼 남발 금지

      • 공통 유틸이 필요하면 별도 share 패키지 고려

    3) 네이밍 규칙(권장)¶

    Controller / DTO¶

    • Controller: {Domain}Controller (예: AuthController, RoomController)

    • Request: {Action}{Domain}Request 또는 {Domain}{Action}Request

      • 예: LoginRequest, CreateRoomRequest

    • Response: {Action}{Domain}Response 또는 {Domain}Response

      • 예: LoginResponse, RoomSummaryResponse

    Service / Command / Query¶

    • Service 인터페이스: {Domain}Service

    • 구현체: {Domain}ServiceImpl

    • Command: {Verb}{Domain}Command

    • Query: {Verb}{Domain}Query

    Data¶

    • Entity: {Domain}Entity

    • Repository: {Domain}Repository (기술에 따라 JpaRepository/Mapper 등)

    4) DTO 변환 규칙(고정)¶

    • api.request → service.command/query 변환은 Controller 또는 Request DTO에서 수행

    • service → api.response 변환은 Controller에서 수행

    • 엔티티를 그대로 response로 내보내지 않는다.

    권장 패턴:

    • LoginRequest.toCommand()

    • RoomSummaryResponse.from(model)

    5) 금지 규칙(필수)¶

    • api.controller에서 data.repository 직접 호출 금지(반드시 service 통해서)

    • api.request/response를 service의 입력/출력으로 직접 사용 금지(원칙)

    • data.entity를 API 응답으로 직접 노출 금지

    • 외부 연동 코드를 service나 api에 직접 작성 금지(data.external로 이동)

    6) 도메인별 하위 패키지 권장(규모 커질 때)¶

    request/response/command/query/entity가 커지면 도메인별로 하위 폴더를 만든다.

    예:

    api/request/auth/...
api/response/rooms/...
service/command/rooms/...
data/entity/rooms/...

    7) 예시 흐름(로그인)¶

    1. api.request.LoginRequest (validation 포함)

    2. AuthController에서 toCommand()로 변환

    3. service.service.AuthService#login(LoginCommand) 호출

    4. AuthServiceImpl에서 data.repository.UserRepository 사용 + 비즈니스 검증

    5. 성공 시 Result.ok(userId) / 실패 시 Result.fail(error)

    6. Controller에서 결과를 api.response.LoginResponse로 변환하여 반환
