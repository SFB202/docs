    유닛 테스트 컨벤션¶

    1) 테스트 범위 정의¶

    Unit Test가 다루는 것¶

    • Service / Domain / Policy / Validator 등 비즈니스 로직 검증

    • 외부 의존성(Repository, Encoder, 외부 Client 등)은 Mock으로 대체

    Unit Test가 다루지 않는 것¶

    • DB/네트워크/파일/메시지 브로커 등 I/O

    • Spring Context 로딩 / Security 필터 체인

    • 위는 통합/슬라이스 테스트로 분리

    2) 디렉토리/클래스/메서드 네이밍¶

    위치¶

    • src/test/java에서 운영 코드 패키지 구조를 그대로 미러링

    클래스명¶

    • {TargetClass}Test (예: UserServiceImplTest)

    • 클래스 @DisplayName("... 유닛 테스트") 권장

    테스트 메서드명(필수)¶

    • “메서드 + 조건 + 결과(Result 상태/에러)”가 드러나야 한다.

    • 예시

      • createUser_newLoginId_returnsOk()

      • createUser_duplicateLoginId_returnsFailConflict()

      • loginUser_wrongPassword_returnsFailNotFound() (정책에 맞게)

    @DisplayName에는 “시나리오 설명 + 기대 결과”를 문장으로 적는다.

    3) 테스트 구조 (Given / When / Then 고정)¶

    모든 테스트는 순서를 강제한다.

    1. Given: fixture 생성 + mock stub

    2. When: SUT 호출

    3. Then: Result 계약(성공/실패) + 값/에러 + 필요 시 상호작용 검증

    4) Result<T> 계약(Contract) 기반 테스트 규칙 — 핵심¶

    너의 Result<T>는 아래 계약을 가진다.

    • 성공:

      • result.isSuccess() == true

      • result.isFailure() == false

      • errors.isEmpty() == true

      • 값이 있는 타입이면 getValue().isPresent() == true

    • 실패:

      • result.isFailure() == true

      • errors.size() >= 1

      • value == null(직접 접근 불가면 getValue().isEmpty()로 검증)

    4.1 메서드별 최소 테스트 수¶

    • 성공 케이스 최소 1개

    • 실패 케이스는 실패 분기(에러 상황) 1개당 1개씩

      • 예: NotFound, Conflict, Validation, Forbidden 등

    4.2 성공 케이스에서 반드시 검증할 것¶

    • assertTrue(result.isSuccess())

    • assertTrue(result.getErrors().isEmpty())

    • 값 검증(가능하면 핵심 필드 비교, toString() 비교 지양)

      • assertEquals(expectedId, result.getValue().orElseThrow())

    4.3 실패 케이스에서 반드시 검증할 것¶

    실패 테스트는 “실패하면 어떤 에러가 있는지”를 고정해야 한다.

    • assertTrue(result.isFailure())

    • assertNotNull(result.getErrors())

    • assertFalse(result.getErrors().isEmpty())

    • 첫 에러(또는 특정 에러)에 대해 아래 중 최소 2개 이상을 검증:

      1. error.getCode() 또는 error.getStatus() (권장 최우선)

      2. error.getMetadata()의 key 존재/값 일치(가능하면)

      3. 에러 타입(class) 고정이 필요하면 assertInstanceOf(...)

      4. message는 전체 문자열 고정 금지(필요 시 contains 정도만)

    권장 우선순위: (1) code/status → (2) metadata → (3) type → (4) message

    4.4 복수 에러(List) 가능 시 규칙¶

    • 에러 “순서”에 의존하지 말 것

    • stream().anyMatch(...) 또는 contains 기반으로 검증

    • 최소 1개 테스트는 “에러 개수 + 특정 code 포함”을 검증

    5) Fixture Monkey 컨벤션¶

    5.1 기본 설정¶

    • FixtureMonkey.builder().defaultNotNull(true).build() 사용 OK

    5.2 생성 원칙¶

    • 분기/조회에 영향을 주는 핵심 필드는 랜덤 금지

      • 예: loginId, userId, roomId 같은 repository 조회 키

    • 실패 케이스는 “분기 조건 필드만 의도적으로 깨기”

      • 예: 존재하지 않는 ID, 중복 키, 잘못된 비밀번호 등

    • 비교는 toString()보다 id/핵심 필드 비교

    6) Mockito(의존성) 컨벤션¶

    • Mock 대상: 외부 의존성만

    • Stub: 필요한 값만 최소 지정

    • Verify(선택):

      • 성공 케이스: 중요한 저장/호출이 발생했는지

      • 실패 케이스: 부수효과가 발생하지 않는지가 중요

        • 예: 중복이면 save 호출 X → verify(repo, never()).save(any())

    7) 금지/권장 사항¶

    금지¶

    • ❌ 스프링 컨텍스트 로딩하는 유닛 테스트

    • ❌ 성공인데 errors 비었는지 확인 안 함

    • ❌ 실패인데 “에러 타입만” 확인하고 code/status 검증 안 함

    • ❌ 랜덤 데이터가 분기에 영향을 주는데 통제하지 않음

    • ❌ 객체 비교를 toString()으로만 하는 것(가능한 경우)

    권장¶

    • ✅ 실패 테스트는 code/status + (metadata 또는 type)까지 고정

    • ✅ 실패 케이스에서 중요하면 never()로 side effect 방지 검증

    • ✅ 메시지는 전체 고정 대신 contains(문구 변경에 강함)

    8) 리뷰 체크리스트(통과 기준)¶

    • 각 기능(메서드)마다 Success 1개 이상 있는가?

    • 실패 분기마다 테스트가 있고, “어떤 에러인지(code/status/metadata)”가 고정되는가?

    • Result 계약(성공이면 errors empty / 실패면 errors non-empty)을 항상 검증하는가?

    • FixtureMonkey 랜덤이 분기에 영향 주지 않게 핵심 필드를 통제했는가?

    • 필요한 경우 실패 시 부수효과 없음(never) 검증이 있는가?
